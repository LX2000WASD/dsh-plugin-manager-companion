# 参考不复制：新仓库的代码引入规范

> 用户明确要求："对于旧有的可复用代码我们的态度是参考但不直接复制粘贴使用。
> 一方面是因为我们的代码有之前的包袱与依赖，一方面是我们的代码实际上可能有许多 BUG 和漏洞。"
> 本文把这条原则变成**可执行的准入规则**，避免执行时走样。

## 1. 三分类准入

每个要从旧仓库搬的能力，必须先归入以下三类之一，并在实现前写下归类理由。

### A 类：重写（默认）
**适用范围**：任何触碰官方契约、写文件、调子进程、管生命周期的代码。

判定：如果它 **import 官方包** / **写 profile 文件** / **起子进程** / **有状态**，一律重写。

理由：旧代码的这些部分是为"官方没有管理页"的世界写的，前提已经消失；
且调研已实证其中有真实缺陷（见 §3）。

### B 类：参考算法后重写（纯函数）
**适用范围**：无副作用的纯计算——打分、排序、标签、分类计数、模糊匹配。

判定：函数签名不含 `Context`/`fs`/`child_process`，输入输出都是 JSON-safe 数据。

做法：**读旧实现理解意图 → 写新实现 → 用旧实现的历史测试当对照**（不复制测试代码，复制用例语义）。

### C 类：仅作需求参考（不写代码）
**适用范围**：UI 交互、页面布局、文案组织。

做法：只看它解决了什么问题，用官方 primitives 重新设计。

## 2. 强制检查项（每个模块开工前）

写任何模块前，先回答：

1. **官方有没有现成的？** 有 → 直接用，不许重写（查 `./operations`、`./types`、`ctx.remote.*`、`ctx.settingsScope`）
2. **旧代码里对应的是什么？** 读它，理解它解决的问题
3. **它属于 A/B/C 哪类？** 写进模块头注释
4. **它的前提还成立吗？** 若前提消失（如"官方没有管理页"），结论必须重推

## 5. 每个模块的交付模板

```ts

 * <模块名> — <一句话职责>
 *
 * 归属：<A 重写 | B 参考重写 | C 需求参考>

```

## 6. 完成判据

一个模块算"完成"必须同时满足：

- [ ] 头注释按 §5 模板写全
- [ ] 官方有现成能力的地方**没有**自己实现
- [ ] 不写 profile 文件、不调 pnpm（除非走官方 `operations`）
- [ ] 有测试，且测试 import **构建产物**（`dist/*.js`），不是源码
- [ ] 若涉及官方契约，有对应的契约测试（如平台表、slot 注册面）
## 7. 工具使用红线（事故驱动，2026-09-18 记录）

### 7.1 绝不把「部分读取」的内容整文件回写

**事故**：为了把备份类型收敛到 types.ts，用 read 读了 src/envManager.ts 再 write 回写。
read 默认只返回 2000 行，而该文件超过这个上限 —— 回写把文件尾部整段截掉（丢失整个备份段）。

**根因**：read 的返回值同时包含 `lines` 与 `totalLines`，但回写时没有比对二者。

**硬规则**：
- 若 `lines.length !== totalLines`，说明读到的是**片段**；此时**禁止**用它做整文件 write。
- 需要改大文件的局部时，用 `edit`（字面替换）而不是 read+write。
- 需要整文件重写时，先确认 `lines.length === totalLines`；否则分批读全再拼，或用 edit。
- 大文件（>1500 行）默认按"只改局部"处理。

### 7.2 破坏性文件操作前的自保

- 大文件在动手前先做一份副本（`cp x.ts /tmp/x.ts.bak`），或在 git 里先提交一次。
- 本仓库尚未建首个 commit，这会让事故无法用 git 回滚 —— 建仓后应尽早提交首个快照。

### 7.3 恢复源优先级

1. 作者本人的上下文（冷启动原作者重写，保真度最高）
2. 构建产物（dist/*.js 含完整实现，dist/*.d.ts 含完整类型面）
3. 测试文件（行为契约，可当正确性依据）

事故恢复实例：envManager.ts 被截断后，用 dist/envManager.js（完好的编译产物）+
env-dev 的原始意图重建；tests/envManager.test.mjs 作为验收依据。
### 7.4 警惕自证式测试（本轮最贵的一课）

**事故**：host 的 `diagnose` 返回裸 jobId 字符串（违反自家 `docs/REST-CONTRACT.md` 的 `{ jobId }`），
而 `tests/index.test.mjs` 的 12 个 op 分派用例**全部通过**——因为测试里的 `makeJobs()` 桩件
返回的也是字符串：**测的是我自己的错误实现，而不是契约**。

后果：真实浏览器里 `report.counts` 读字符串属性抛错 → 官方 SlotErrorBoundary 接住 → **整页空白**。
单测全绿、SSR 全过，用户看到的是白屏。

**规则**：
- 桩件要按**契约**建模，不是按实现建模。实现与契约不一致时，测试应当红。
- 契约里写死了形状的边界（如首包 `{ jobId }`），就写一条**钉形状**的断言，
  并且刻意**不接受**"宽容"形式（见 `tests/index.test.mjs` 的 `jobIdOf()`）。
- **单测 + SSR 绿 ≠ 用户能用**。任何"渲染出来"的断言，最终要有一条走真实浏览器的路径
  （`tools/cdp-shot.mjs` + `tools/e2e-visual.mjs`）。
- 独立审计者的价值在于**不共享作者的盲区**。作者自查发现不了自己的系统性错误，
  这不是态度问题，是信息问题。

### 7.5 「可连接」不等于「可用」（2026-09-19 记录）

**事故**：startEnvironment 用「TCP 端口可连接」当作实例就绪。真机实测它 1018ms 就返回
ok=true 并给出地址，而那一刻 GET / 返回 **404**（服务器已绑定端口、路由尚未注册），
1000ms 之后才是 **401**（官方 browser-auth 的未授权应答，说明 GUI 路由已注册）。
用户拿到的是一秒钟内打不开的地址。

**同一轮的第二处**：createEnvironment 不带模板时走官方 DEFAULT_PROFILE_BUNDLES =
['@deepseek-ai/dsh-base']（只有 base，没有 web server），于是**新建的环境必然启动超时** ——
30 秒干等，最后一句「请看启动窗口的输出」。264 个单测全绿、16 项视觉 e2e 全绿都没发现，
因为 e2e 跑的是「复制 pm-test 的文件 + pnpm install」的临时 profile，
**从没调用过我们自己的 createEnvironment**。

**规则**：
- 判据取**用户能观察到的那一步**。不是「端口在监听」，而是「官方 HTTP 端点已按官方语义应答」。
  能观察到的事实在哪一层，判据就取到哪一层。
- **e2e 的起点必须是产品的起点**。跑在别人造好的 profile / 别人准备好的状态上，
  等于绕开了最该验证的那段代码；验收路径要自己从 0 走到用户看到的结果。
- 测试绿 ≠ 用户能用，这一点已在 §7.4 记过一次；§7.5 是它在**生命周期与就绪**上的同型复发。
  凡新增一条「等待某外部条件」的逻辑，都要问：**条件成立时，用户能做的事真的能做成了吗？**
- 该提前判定的事不要拖到超时。能读到官方事实（如环境的 bundle 层栈）就在动手前判定并
  给出可操作的说明（「请启用 X」而不是「请看窗口输出」）。
- 官方常量优先：层栈与模板来自官方 PROFILE_TEMPLATES / DEFAULT_PROFILE_BUNDLES，
  不抄成我们自己的名字表——抄一份就是一份会过期的假事实。

### 7.6 测试读的是构建产物，不是源码（2026-09-19 记录）

tests/*.test.mjs 一律 import ../dist/*.js。由此产生一条纪律：

- **验收命令只有 `pnpm test`**（它先 `pnpm run build` 再跑 node --test）。
  直接跑 `node --test 'tests/*.test.mjs'` 等于拿"碰巧摆在 dist 里的那一份"当被测物：
  别人正在编辑 src 时你会跑在坏掉的构建上；没人编辑时你会跑在**过期**的构建上——
  后者更危险，因为它是静默的假绿，与 §7.4 同族。
- 本轮实证：env-dev 撞到 engine-dev 编辑中的 src/diagnostics.ts 让 dist 无法加载；
  write-auditor 也直接用 node --test 跑过一轮（结论恰好可信，那是运气，不是方法）。
- 报"测试通过"时必须说明用的是哪条命令。用 node --test 直跑的结论不算验收，
  最多算"我本地看起来没问题"。
- 不为此加 mtime 新鲜度启发式：它会制造假红，而假红会让门禁失去可信度——比假绿更难恢复。
- **一次全绿只有在"没有写者正在编辑 src"时才成立**。本轮 Lead 在提交前跑门禁就撞到过一次：
  同一个仓库、相隔几十秒，先红（写手改了文件、build 抓到一个不一致的中间态）后绿（写手落地后 295/295）。
  并发编辑期间的绿与红都不能当结论——验收必须等所有写者停下，并且在提交前重跑一次。

### 7.11 取证脚本不得写入用户的全局状态（2026-09-19 记录）

事故：暗色审计为了切主题，走了官方「设置 → 通用设置 → 外观 → 深色」这条路——而那条路会**持久化到用户的全局设置**
`~/.dsh/settings.yaml`（`ui-theme.preference: dark`，mtime 与取证时间一致）。也就是说：一次只读性质的审计，
**改掉了用户正在用的 GUI 的外观**。

这与 §7.7（端口归属）是同一类问题：**测试手段本身有副作用，而副作用落在了用户身上**。

规则：
- 取证/测试需要改变外观、配置、环境状态时，用**临时 `DSH_HOME`**——我们已经这么建临时 profile 了，
  但**全局设置文件不在 profile 里**，这是本次漏掉的那一环。
- 需要切换界面状态但不想持久化时，优先用**只影响当前会话的手段**（直接改主题服务写的 DOM 属性、注入样式），
  而不是走会写盘的 UI 路径。
- 取证结束前**核对一次自己有没有写盘**（settings / profiles / 记录文件）；写了就在回报里**明确写出来**，
  不要当成没发生——本次是 ui-dev 在旁证时先发现的。
### 7.9 换源码不等于换被测物：不要用 git stash 做 A/B（2026-09-19 记录）

engine-dev 为了判断一条测试失败是不是自己造成的，用了 `git stash` 回到旧源码，然后跑测试，
得出「这条失败是既有的、与我的改动无关」。**这个结论是错的**：`git stash` 只回退了**源码**，
`dist/` 里仍然是**他自己构建的那一份**——所谓「旧代码」从来没有被跑过。后来他补上桩件、测试转绿，
主动更正了这个判断。

规则：
- 做 A/B 对照必须在换源码之后**重新构建**（`git stash && pnpm run build:host`），或者干脆用 `git worktree`
  另开一份干净树；否则你测的还是自己的构建。
- 这是 §7.6 开头那条（测试读的是构建产物）的另一种表现形式：**换源码不等于换被测物**。
- 凡是「这条红是不是我造成的」这类结论，都要说清被测物是哪一份产物——与 §7.8 是同一件事的两面。
### 7.10 共享文件的写权：在途者优先，后来者等并重读（2026-09-19 记录）

共享文件被多个任务同时改，本轮撞了两次：`tests/console-page.test.mjs`（task-34 与 task-35）与
`src/client/locales.ts`（task-41 / task-47 / task-48 三方同写）。写范围只是**声明**，不是锁；
靠"应该不会撞"来协作一定会撞。

规则：
- **在途者优先**：已经开工并改着这个文件的人继续做完，后来者不要插入；
  若在途者做的是更高优先级的事（例如修一个"功能坏了"的 P0），优先级压过"我来做文案清理"。
- **后来者动手前必须重读该文件**，并在做完后把**改过的键名或行范围**同步给下一个写者。
- 排不出顺序时**回报 Lead 裁定**，不要自己一边改一边赌。
- 能并行就别串行：把不依赖该文件的部分（只读审查、报告、只属于自己文件的护栏）先做掉。
**提交时不要用 `git add -A`。** 在并发写窗口里它会把你没打算提交的、别人正在改的文件一起扫进来。
本轮真发生过一次：Lead 提交一个批次时用了 `-A`，把 engine-dev 在 task-55 里正在改的 `diagnostics.ts`
与 `docs/OFFICIAL-DEPENDENCIES.md` 一起带进了另一个任务的提交里，导致他那份交付"分属两个提交"，
对账时得额外解释一遍。

规则：
- 提交前**按路径显式 `git add`**，只加这个提交要讲的那几个文件；
- 加之前先 `git status --porcelain` 看一遍：**凡是你叫不出"它属于哪个任务"的文件，就不要加**；
- 确实需要整体提交时（例如几个文件互相依赖、只提一半会编不过），在提交信息里**写明**在途部分是谁的、哪个任务。
### 7.8 真机结论必须钉在一次具体构建上（2026-09-19 记录）

auditor 在收尾核对时发现自己的问题：报告里的三条真机结论**没有记下对应哪份产物**，
而仓库里的 ConsolePage.tsx 在结论之后又被改过、dist 也重建过——于是没人能判断那三条结论
到底是对哪一版成立。他随后重跑一次、并把「本节所有结论对应构建 dist/client.js <时间戳>」写进报告。

规则：
- 真机（浏览器 / REST / CLI）结论一律附上**产物标识**：至少记 dist 的时间戳或 md5，条件允许时连 git HEAD 一起记。
- 写「修复后复验」时要同时给出**修复前的基线**和它对应的产物——否则前后两次跑的不是同一份东西，结论无法对比。
- 与 §7.6 的关系：§7.6 管「跑的是不是最新构建」，§7.8 管「结论钉在哪份构建上」。两条一起才闭环。
**取证件本身也要钉在出厂内容上。** market-dev 在刷新市场页截图时发现一个静默漂移：验收驱动的判定串等的是
**旧文案**（「这是缓存索引」），而产品的出厂文案已经被精简掉了——于是"图看着对"，但驱动脚本其实在等一个
不再存在的串，一旦文案再改它也不会响。他把判定串改成按出厂文案断言，并留下一句判据：**文案再改，这里要红**。

规则：凡是「用脚本验证界面文案/呈现」的地方，判定串必须取自**当前出厂内容**（字典或源码），
不能取自某一次取证的快照；否则证据与产品会各走各的，而且**不会有人发现**。
### 7.12 变异脚本必须检查构建退出码（2026-09-20 记录）

事故（task-90）：两条变异（M2/M3）第一轮报的是"**绿 ✗ 变异没被抓住**"。
查下去不是判据弱，而是**变异根本没生效**：

- M2 把 `plan.keep.length === 0` 改成 `true`，TypeScript 因此报 `'plan' is possibly 'undefined'`
  （窄化失效）→ `pnpm run build` **失败** → `dist/client.js` 保持旧内容 →
  测试跑的是**未变异的产物**，当然绿。
- 而脚本写的是 `pnpm run build >/dev/null 2>&1`，**丢掉了退出码**，把"构建失败"当成"构建成功"。

这与 §7.4（自证式测试）同族：**用代理判断代替事实**。绿的是"构建命令返回了"，不是"变异生效了"。

约定：

- 变异脚本里 `pnpm run build` **必须**判退出码；失败就报"变异无效"，**不许报绿**，并打印编译错误。
- 变异"应用没应用上"也要判：模式串没匹配到就报"没应用上"，不要静默跳过（那同样是假绿）。
- 报"变异被抓住"时，**红输出必须来自变异本身**：先看构建成功、再看用例名对不对得上。
  本轮 M3 第一次也报绿——原因更细：我只改了 remove 那一处的拼接，而触发 R2 的那条 reason
  在 **keep** 分支（`正在运行：不删…` 自带冒号）。变异改错了地方，等于没改。
- 判据是"**变异改的是不是那条判据真正读的那条路**"。改错分支与构建失败一样，都是假绿。
- `set -u` 不配 `set -e` 时，任何一步失败都会继续往下跑；变异脚本里每一条外部命令都要显式判退出码。

- 同族的一条（task-90 实测）：**跨不过渲染的接线用源码级断言钉**。
  "用 react shim 把 state 强制打开"只能证明"打开时会渲染成 open"，它**绕过了 onClick**；
  把 onClick 从 `setConfirmingCleanup(true)` 改成直接执行，那条用例照样绿。
  跨模块拼接（host 拼表头、客户端切分）同理——R5 的守卫就是源码级的。
### 7.13 断言不要绑在某句措辞上（2026-09-20 记录）

事故（task-92 / task-93 各一次，都是**我自己写错的断言**，不是产品错）：

**第一次（task-92）**：验"点确认会执行"时，断言写的是
"面板里有『没有需要清理的测试环境』"。而**那句话在点之前就在了**（计划区在空计划时说的就是它）——
断言恒真，点没点都绿。这是 §7.4（自证式测试）的又一例。

**第二次（task-93）**：把上面那条改成"数那句话出现几次"（点前 1 处 → 点后 2 处），确实不恒真了。
但同一轮里产品把结果行的措辞从 `没有需要清理的测试环境` 改成 `已清理 0 个测试环境`——
**那句话在结果行里没了，计数恒为 1**，判据又失效了。

两次的共同点：**判据绑在了"某句具体措辞"上**。措辞是产品最容易变的东西，
而断言的价值在于"行为变了才红"，不是"文案改了也红"。

约定：

- 验"某个动作发生了"时，判据要钉在**只在执行后出现的信号**上，优先级：
  1. **副作用本身**（op 请求记账 / 文件真的被删 / 目录列表变化）——与文案完全无关，最硬；
  2. **只在执行后出现的结构**（`data-*` 状态属性、结果块的 DOM 节点）；
  3. **文案**——只在①②都拿不到时才用，且要挑"只在执行后出现"的那一句。
- 用文案当判据时，**先问一句：这句话在动作之前会不会已经存在？** 会 → 它不能当判据。
- 同理，**断言不要写死措辞的字面量**：要写就写"这一态必须有某个完成态标记"，
  或把措辞的**结构**（有数字 / 有完成态前缀）当判据，而不是整句。
- 与 §7.12 的关系：§7.12 管"变异有没有真的生效"，本条管"判据会不会因为无关变化而失效"。
  两条一起才说明"红"是有意义的红。

- 反面教材（同一族，task-92）：**按钮文案撞车**——触发按钮与确认按钮都叫「清理过期」，
  按文本取"第一个可见的"点到的其实是触发按钮（框已开着 = 空操作）。
  教训：**按可见文本定位控件时，必须限定范围**（哪个容器里），否则同名控件会互相冒充。
### 7.14 截图取证必须断言可见性（2026-09-20 记录）

同一个坑踩了**三次**，每次都是"断言过了，但图上没有"：

| # | 场景 | 假绿长什么样 |
|---|---|---|
| 1 | trial-plan-evidence | 计划区在折叠线以下：`innerText` 读得到，截图里空无一物 |
| 2 | trial-cleanup-confirm-evidence | 点错了**同名按钮**（触发按钮与确认按钮都叫「清理过期」），确认框根本没开 |
| 3 | about-evidence | 未知态与正常态两张图 **md5 完全相同**——降级那一行在折叠线以下 |

共同点：**断言读的是 DOM 的"有没有"，截图拍的是"看不看得见"**。
在滚动容器里这两件事天然不同——`innerText` 会把滚动外的内容一起读出来。
这与 §7.4（自证式测试）、§12.10（代理 ≠ 事实）同族：**"我断言的那个东西"不是"我要证的那个东西"**。

**约定（两条，都必须做）**：

1. **截图前断言目标在视口内**。判据是 `getBoundingClientRect()` 与视口**相交**，
   不是 `offsetParent !== null`（那只说明没被 `display:none` 藏起来，滚动到视口外时仍为真——
   而那正是第 1、3 次事故的形态）。只断言 `scrollTop` 变了也不够：它可能滚过头把目标推到另一侧。
2. **两张声称不同的截图必须断言 md5 不同**。"图看着对"不是判据，md5 才是。
   一个脚本说"浅色一张、深色一张"或"正常态一张、未知态一张"，若 md5 相同，
   就说明**第二张根本没拍到它该拍的东西**。

**工具**：`tools/shot-assert.mjs` 把这两条变成一次调用——
`visibleExpr(selector)`、`scrollIntoViewExpr(selector)`、`shotMd5(path)`、
`assertShotsDiffer(left, right, what)`、`assertShotsDistinct(shots, what)`。
取证脚本不许各写一遍 `md5sum`（写四遍就有四处会忘记）。

**为什么按标签/选择器找元素而不是按位置**：第 2 次事故里两个按钮**同名**，
按"第一个可见的"取到的是错的那个——**按可见文本定位控件时必须限定范围**（容器、角色、位置）。

- 与 §7.12 的关系：§7.12 管"变异有没有真的生效"，§7.13 管"判据会不会因为无关变化而失效"，
  本条管"证据拍到的到底是不是要证的东西"。三条合起来才说明一次取证是可信的。
### 7.15 取证三律：fixture 要真、控件要限定范围、判据范围按规则定义（2026-09-20 记录）

task-97（回滚入口）一轮里**三次"我造的证据是假的"**。三条互不相同，但都是**取证者自己引入的假象**，
不是产品缺陷——所以它们值得单列：**假证据比没有证据更坏**，它会让人以为已经验过了。

#### 一、fixture 必须是**真实存在**的值

为了造"有更新"的状态，我直接把探针里那个包的 `package.json` 的 `version` 手改成 `0.1.0`。
后果：升级"成功"（官方 `add <name>@latest` 不看当前声明），而**回滚装不回一个不存在的版本**
（registry 上只有 `0.1.6-alpha.1` / `0.1.6-alpha.2`）。
那一轮我差点把它报成"回滚有缺陷"——**其实是我造的 fixture 不成立**。

约定：
· 造状态优先用**真实操作**（`pnpm add <name>@<真实版本>`），而不是手改盘上文件；
· 手改盘上文件时必须先问一句：**这个值在真实世界里可能存在吗？**（版本号要去 registry 核）；
· 与 §7.12 同族：§7.12 管"变异有没有真的生效"，本条管"fixture 有没有真的成立"。

#### 二、按可见文本定位控件**必须限定范围**

回滚入口在卡片上叫「回滚到 0.1.6-alpha.1」，确认框里的确认按钮**文案完全相同**。
不限定范围时"点入口"取到的是"第一个可见的"——可能正是框里那个确认按钮，
于是**"必须二次确认"这条护栏被验反了**（测试绿，但验的是相反的行为）。

这与 task-92 的「清理过期」同名按钮、task-96 的两张"官方运行时"卡片是**同一族**，
已进 §12.10 的反面教材。约定：`page` / `modal` 两个范围显式分开，不许取"第一个可见的"。

#### 三、判据范围按**规则自己的定义**选（"这一行" ≠ "这一块"）

同一批渲染文本，喂给同一批判据，**范围选错就是假阳性或假阴性**，而且方向相反：

| 规则 | 它的判据单位 | 选错的后果 |
|---|---|---|
| R2（原因不许冒号套冒号） | **一行**（"同一行两个冒号"） | 整块判：把两个元素凑成一句 → 假阳性 |
| R5（原始日志必须有标识） | **一块**（标识与原文是两个相邻元素） | 逐行判：把 `<pre>` 的每一行都当成裸日志 → 假阳性一串 |
| R6（历史记录必须交代时间性） | **一句**（"上次"与"升级"同句） | 整块判：跨元素凑成一句 → 假阳性 |
| R4（结论只留一处） | **一块**（同一结论出现几次） | 逐行判：永远只数到一次 → 假阴性 |

task-96 踩了 R6 的整块假阳性，task-97 踩了 R5 的逐行假阳性——**两次都是范围错**，方向相反。
约定：用判据前先读它的 `judge` 怎么切分（`copy-rules.mjs` 里每条都写了）；
**不能一刀切"全部逐行"或"全部整块"**。

#### 附：同一 profile 不能并发取证

取证脚本会**真的改探针环境**（装/卸包、改盘上版本）。两个任务同时跑会争用同一个 profile，
双方都拿到半真半假的状态，那一轮结论全部作废（task-97 实际发生，只能杀掉重跑）。
规矩写在驱动脚本的头部：**取证串行跑**，起新的之前先确认没有旧的还在。
