# dsh-plugin-manager-companion · 设计定稿

> 本文件是新仓库的**唯一设计权威**。所有实现决策以本文为准，偏离必须先改本文。
> 前身：`dsh-web-plugin-manager`（0.6.3，已停止维护，README 将注明由本仓库接续）。
> 官方基线：DSH `>= 0.1.6-alpha.2`。

## 0. 一句话定位

**官方插件管理器的伴生补强**：官方管"装什么、开什么"，我们管"装得对不对、环境健不健康、整个机器怎么管"。

## 1. 与官方的分工（不可越界）

| 能力 | 官方 | 我们 |
|---|---|---|
| 组合包启停 / 行级开关 | ✅ 已做 | ✗ **绝不做** |
| bundle 安装 / 卸载 | ✅ 已做 | ✗ **绝不做**（只在安装前插质量门）|
| 插件配置页托管 | ✅ 提供 slot | ✅ **作为注册方**接入 |
| 安装前静态质量门 | ✗ 不做 | ✅ **做** |
| 深度环境诊断 | ✗ 不做 | ✅ **做**（核心）|
| 多 profile 环境管理 | ✗ 明说"不能改另一个 profile" | ✅ **做** |
| 插件市场 | ✗ 无概念 | ✅ 做（不主打）|
| skill / agent 预设 | ✗ 明说"仍是文件操作" | ✅ **做** |

**硬约束**：所有当前 profile 的写操作走官方 `ctx.remote.pluginManager`；跨 profile 走官方 `./operations` 的 `runPluginCommand`。**我们不自己写 `cordis.patch.yml`，不自己调 pnpm。**

## 3. 页面结构

### 3.1 一级设置页（`settings.section`）

官方 order 布局：`general=0, models=10, plugins=15, agent-presets=20, archived-sessions=25`

| id | order | 名称 | 内容 |
|---|---|---|---|
| `marketplace` | 16 | 插件市场 | 索引浏览、搜索、分类、安装（走官方）|
| `console` | 17 | **环境控制台** | **健康检查 + 环境管理合一**（见 §4）|
| `kinds` | 22 | 技能与预设 | SKILL.md / agent.cordis.yml 直装 |

### 3.2 官方插件页内的注册（"点开即可管理"）

按官方 `slot-contract.ts` 声明，**注册方与页面同生**：

| slot | key | 我们注册什么 |
|---|---|---|
| `plugins.item` | — | 我们自己的条目卡片（label 用字典）|
| `plugins.bundle.config` | `dsh-plugin-manager-companion` | 本插件在**官方插件页**的配置表单 |
| `plugins.row.config` | `<包名>#<行 id>` | 需要逐行配置的组件 |

**已实证**：`PluginManagerPage.tsx:966` 的 `configured = ledger.bundles.has(openPkg.name)`，用自己包名注册即渲染。

### 3.3 配置写入：不编辑配置文件

用官方 `ctx.settingsScope.bind({ namespace })` + `register()`（`SettingsProvider`），
用户在我们的表单里改，**由官方 settings 服务落盘**。我们不碰 YAML。

## 4. 环境控制台（合并页，本仓库的核心）

用户定位："类似 360 电脑管家"——**对本地 DSH 环境做深度、可视化的分析与管理**。

### 4.1 设计原则

- **只读优先**：默认只诊断、不修改；任何写操作都要明确点击 + 行内确认
- **证据可溯**：每条诊断都能点到源文件/行，不做黑盒判断
- **官方事实优先**：能用 `ctx.reflect`/`ctx.loader` 读到的，不靠源码正则猜

### 4.2 诊断维度（分层）

| 层 | 数据源 | 检测项 |
|---|---|---|
| L1 依赖 | 静态扫描（package.json + import 图）| 缺失依赖、未声明 import、官方包重复、peer 版本 |
| L2 组合 | 官方 `composeEntries` + patch 层栈 | 行 id 重复、被禁用依赖、遮蔽、孤立行 |
| L3 运行时 | `ctx.loader.entries()` + `ctx.reflect` | fiber 相位异常、pending 根因、失败原因、服务名冲突 |
| L4 一致性 | 官方 `readPluginInventory` vs 本地文件 | 声明未装、装未挂载、挂载未声明 |
| L5 生态 | 市场索引 | 更新可用、已知风险徽标、废弃包 |

### 4.3 分级处置

- **A 级（可安全自动修）**：重复行 id、官方包重复、被禁用依赖 → 一键修复
- **B 级（需确认）**：同名注册冲突、缺失依赖 → 建议 + 行内二次确认
- **C 级（只报告）**：循环依赖、peer 不满足、语义冲突 → 输出 + 溯源

### 4.4 环境管理（同一页面）

- 环境列表（运行状态、端口、进程）
- 启停（终端/后台，端口探测）
- 创建 / 重命名 / 删除（官方 profile 只读保护）
- 插件跨环境复制/转移
- 备份导出 / 差异对比 / 导入恢复

**写路径**：官方 `runPluginCommand({ profile, dir, installAnchor, cwd, home })` + `withFileLock`。
**恢复路径**：官方 `sanitizeProfile(binName, profileDir, bundles)`。

## 5. 质量门（安装前拦截）

```
1. inspect(spec)                              ← 官方 Remote
2. installBundle(spec, { enabled: false })    ← 官方 Remote（装但不激活）
3. 扫描已安装包（我们的质量门）                ← 独有
4. 不合格 → removeBundle(name)                ← 官方回滚
   合格   → setBundleEnabled(name, true)      ← 官方激活
```

零竞态、零自建 pnpm、零 patch 写入。官方 UI 自己就用 `enabled: false`（`manager-store.ts:561`）。

### 5.1 第一步：静态快筛（已实现）

上面那四步就是快筛：装但不激活 → 扫包 → 放行或回滚。它是**只读文件**的，成本 60–79ms，
能抓住"装进去就炸"的那一类：未声明 import、声明了没装、官方包被声明成普通 `dependencies`、
入口解析不到、bundle patch 行解析不到。

**它抓不到"只有真挂载才暴露"的那一类**（实测 3 种坏法只抓到 1 种），所以需要第二步。

### 5.2 第二步：试装（真实安装验证）

**目标**：在用户点"安装"时，先把候选包装进一个测试环境并**真的启动一次**，看它能不能被挂载。
实测对照（三种坏法注入真环境逐个 boot）：patch 行挂 import 不到的模块 → 静态门也抓到；
模块 `apply()` 启动期抛错 → 只有启动抓到；服务名冲突（占 `pluginManager`）→ 只有启动抓到。
**真实启动 3/3，静态门 1/3**。两者是接力不是替代：静态门 60–79ms 做前置快筛，试装做最终判定。

**验证形态（不得偏离）**：

- 官方**没有**"启动 + 验证 + 退出"模式（`apps/cli/src/args.ts` 的 `DshInvocation` 只有 profile / dump-config / plugin）。
- `--dump-config` 60–79ms 且**不加载任何 JS** → 抓不到 import/apply/服务冲突，只能当组合层快筛。
- 真验证只能用 **headless 启动且不给任务**：519–558ms，真挂载整棵树，拆除 2ms。
- **退出码不可用于判定**——健康环境也是 exit 1（官方以"缺任务"收场）。判定读 stderr 特征：
  正常只有一行 `dsh: a task is required…`；失败是 `plugin tree failed to load` + 44–52 行 cause 链。
- **绝不传任务文本**。实测 `env -u DEEPSEEK_API_KEY` + `stdin=/dev/null`：不需要 key、不调模型、
  无 session 落盘（只多一个 223 B 的 `cordis.yml`）。给任务就变成"真跑一轮 agent"，那是花用户的钱。

**受控对照四步（缺一步结论就站不住）**：

```
① 物化快照 → ② 基线启动 → ③ 装候选包 → ④ 二次启动
   ②失败 → 如实说"当前环境快照本身就起不来"，不赖候选包（并把这个发现升级成一条诊断）
   ②成功 ④失败 → 这才是"候选包导致的"，给出 stderr 根因链
   ②成功 ④成功 → 通过
```

②那一步多花 558ms，但把结论从"失败了"变成"**是它导致的**"。默认开启，可在设置里关。

**成本（全部本机实测，含口径）**：

| 步骤 | 耗时 | 磁盘 |
|---|---|---|
| 建测试环境（headless） | 34ms | 488 B / 12 KiB 块；**无 node_modules**（依赖由安装锚点解析）|
| 浅快照（只复制清单文件） | 毫秒 | KB 级 |
| 真实快照（`pnpm install --prefer-offline`） | 831ms 冷 / 59ms 热 | 看似 +9.3 MiB，但因 **pnpm 硬链接**（1243/1247 文件 nlink>1）store 增量为 **0**，**独占占盘仅 36 KiB** |
| 装候选包 | `link:` 33ms；registry 冷 store + 联网 1159ms、热 29ms | 冷 store 时 store +4.0 MiB |
| 启动验证 | 558ms（复跑 524ms），拆除 2ms | 块 I/O 读 0 写 0 |
| **一轮完整试装** | **≈0.65s**（冷 store + 联网下载候选包 ≈2.3s） | —— |

**内存峰值 ≈161 MiB/次验证启动**（maxrss）。磁盘几乎不要钱，内存才是真实成本，
UI 必须如实告知——它是"点一下会发生什么"的一部分。

**试装会真的执行第三方代码**：候选包被真实安装进测试环境，带 `postinstall` 的包会在用户机器上真的跑。
接受这条风险是本功能成立的前提，因此必须**显式开启 + 明确告知**（默认关闭）。
让第三方代码不在真实环境里执行需要自建沙盒，列入路线图（§10），不在本轮范围。

**失败的三种结论各有措辞**，不得混：`快照基线就起不来`（不是候选包的问题）/ `候选包导致挂载失败`（给根因链）/
`无法试装`（例如禁用联网且本地 store 没有该包）——最后一种**不能算通过**。

### 5.3 试装的设置项

放在「环境控制台 → 设置」子页（字段多且需要解释，塞进官方 bundle 表单会很难看；
两处共用同一个 settings store，所以在官方插件页也能看到这些键）。

| 选项 | 默认 | 说明 |
|---|---|---|
| 试装总开关 | **关** | 打开时明确告知：会在你机器上真实安装候选包并执行它的安装脚本 |
| 快照深度 | 自动 | 自动判定：层栈全可由安装锚点解析 → 浅快照；否则走真实快照。可手动强制"真实快照" |
| 试装前做基线启动 | 开 | 见 §5.2 四步里的②；关掉省 558ms，但失败时说不出是谁的问题 |
| 允许联网拉取候选包 | 开 | 关掉则只用本地 store，冷包直接判"无法试装"（如实说，不假装通过）|
| 试装失败时的行为 | 阻止安装 | 另一档：只警告，由用户决定 |
| 自动清理测试环境 | **开 / 14 天** | 时间可改；可整体关掉自动删除 |
| 最多保留测试环境数 | 不限 | 不设硬上限，但设置页显示**总占地** |

### 5.4 测试环境与状态同步

**命名与归属**：`<当前真实环境名>-dpmc`，一个真实环境对应一个测试环境（保真需要）。
它在环境列表里必须一眼可辨、禁止重命名，且不得被当成真实环境操作。

**同步原则：不订阅变化，使用时即时物化。**

用户可能在终端里跑官方 `dsh plugin add`、也可能直接改本地文件——这些外部改动**不可能被通知**
（官方没有这类事件钩子）。但**不需要被通知**：只要我们在"要用它的那一刻"重新读一遍磁盘事实，
看到的就是最终状态。订阅需要钩子，拉取只需要能读文件系统。

机制四步：

1. **环境指纹**（五元组，**全部读盘，不读我们自己的内存台账**）：`package.json` 内容 hash +
   `pnpm-lock.yaml` hash + `cordis.patch.yml` hash + 官方 `listBundles()` 的层栈 + 依赖清单。
   为什么不读台账：用户在终端里的改动不会经过我们，台账必然过期。
2. **每次试装前**：算真实环境指纹 → 与测试环境记录的指纹比对 → 不一致就重新物化。
   代价可接受，因为试装是事件驱动的（只在用户点安装时发生），不是周期任务。
3. **结果带快照标识**：指纹 + 时间戳，UI 写一句事实"基于 N 分钟前的环境快照"。
4. **试装后再算一次指纹**，不一致就如实说"试装期间环境又变过，这个结论可能不适用"。

残留的是"快照瞬间 → 试装完成"这几秒的竞态，**不可消除**（真实世界就是会变），
能做的只有第 4 步的如实标注——不说"没问题"，只说"基于什么、结论是什么、还缺什么"。

**测试环境永不是真值来源**：不向上同步、不参与诊断结论、删除必须安全（正在运行则先拒或先停）。

**清理**：默认开启自动清理、保留 14 天，用户可改天数或关掉。删除前只针对形如 `<名>-dpmc` 且确认
属于我们的环境；真实环境被改名/删除后遗留的孤儿测试环境同样纳入清理范围。删除动作记日志（删了哪个、为什么）。

## 7. 已知必须修的旧代码缺陷（参考不复制）

## 11. 传输层决策（实施期补充，取代第 8 节该行的笼统表述）

第 8 节写的"跨端：ctx.remote.<ns>.<method> 替代自建 REST"只对**官方能力**成立。
实测后的精确划分：

| 调用目标 | 通道 | 依据 |
|---|---|---|
| 官方能力（pluginManager.*、pluginInventory.*） | **官方 Typert Remote**，`ctx.remote.<ns>.<method>` | 官方在 `api-remotes` 里按 build-time value import 挂载；第三方可直接注入使用 |
| 本插件自有能力（诊断/环境/市场/技能/配置） | **自有 REST**，注册在 `ctx.webServer.register` | 见下 |

### 为什么自有能力不用官方 Remote

官方 `api-remotes` 的能力集合是**编译期 value import 固定的**（其 README 明说"增加能力需显式
/remote import 与 mount"）。第三方要自带 Remote 就必须用 `@deepseek-ai/dsh-typert-generator`
生成 `./typert` 与 `./remote` 产物；而该生成器在 npm 上的可用版本是 `0.0.1-rc.1`，
远落后于运行时 `0.1.6-alpha.2`。用版本错配的生成器产出运行时反射产物，是比 REST 大得多的风险。

`@deepseek-ai/dsh-host-webserver` 的 `WebRoute` / `WebServer.register` 是**官方公开路由 API**，
不涉及生成器。旧仓库已用它跑通完整链路，包括信任围栏。

### REST 契约（host 与 client 的唯一约定）

- 前缀：`/api2/companion`（**避开**旧仓库的 `/api2/plugin-manager`，两包可能短期共存）
- 只接受 `POST` + `content-type: application/json`
- 信任围栏：Host 必须是回环或白名单；`Origin` 存在时必须同源（防 CSRF/DNS-rebinding）
- 请求体上限分级（默认 1 MiB；备份导入 16 MiB）
- 响应信封：`{ ok: true, value: T }` 或 `{ ok: false, error: { code, message } }`
- 长操作（诊断全量、批量恢复、跨环境 pnpm）必须 job 化：POST 即返 `{ jobId }`，
  客户端轮询 `job` op。理由：HTTP 超时不可与服务端状态脱节。
## 12. UI 文案标准（用户反馈驱动，2026-09-19）

**用户反馈原文**：*"UI 上不要出现类似『诊断、多环境管理都在这一个入口里；写操作一律走官方通道』
这样的解释性段落……官方 DSH 也没有加入这些过于冗余的解释性注释段落在自己的 UI 中。"*

这条反馈是对的，而且它指向一个可判定的标准。

### 12.1 官方标尺（实测文案）

| 官方页面 | 它的 intro |
|---|---|
| 模型设置 | `填入各提供方的 API 密钥即可使用其模型。` |
| 插件设置 | `查看内置部署的插件列表` |

两句都很短，且只回答**"这里能做什么"**或**"这里有什么"**。
官方 UI 里**没有任何一句**解释通道、传输、服务归属或模块结构（grep 过 remote/channel/service/via 零命中）。

### 12.2 硬规则

**一级页面的 intro 最多一句，只描述"这里有什么"或"这里能做什么"。**

禁止出现（三类）：

1. **实现与通道**：`走官方通道` / `由官方 settings 服务落盘` / `不写 YAML` / `经 loader 应用`
2. **结构说明**：`都在这一个入口里` / `和「设置 → 某处」是同一份文档` / `插件本体在官方插件页管理`
3. **自夸**：`如实标注` / `每条发现都能展开证据` / `绝不静默`——做到了自然看得见，写出来是噪声

保留（这些是用户**需要**的）：

- 空态（`还没有通过本插件安装的技能或预设。`）
- 错误与失败原因（`环境不存在：xxx`）
- **用户即将做的动作的后果**（`关闭的层会在体检里跳过`、`卸载后需要重启才完全生效`）
- 加载态、字段标签、占位符、确认按钮文案

### 12.3 唯一判据

> **这句话删掉之后，用户还能不能完成任务？**
> 能 → 删。不能 → 它是必须的信息，保留（并尽量缩短）。

判据本身没问题，但它有个前提容易被跳过：**先看屏幕上已经显示了什么**。
如果这句话提供的信息已经由界面的其它部分提供（列表项、选择器状态、组头计数），
那么删掉它用户当然还能完成任务——**但也因此它本来就不该存在**。

2026-09-19 的教训：本节曾写着「五层诊断：依赖、组合、运行时、一致性、生态。保留前半（用户要认识这五个词）」。
这是错的——那五个层的名字**就在下面逐个显示着**，intro 只是把屏幕上的东西又念了一遍。

### 12.3.1 第二次反馈补充的四类（2026-09-19，用户逐条举例）

用户给了三个实例，它们共同指向四类必须删的文案：

| 类 | 实例 | 为什么删 | 正确形态 |
|---|---|---|---|
| **重复屏幕已有信息** | `五层诊断：依赖、组合、运行时、一致性、生态` | 层名就在下面显示着 | 删（或什么都不写）|
| **解释设计意图** | `默认诊断当前环境` | 页面打开就显示当前环境，选择器也可见，不言自明 | 删 |
| **状态写成句子** | `选中其他环境后本页只读` | 状态是**事实**，不是解释 | 换成选中时的「只读」标记 |
| **总结后的括注** | `同类发现已归并为 3 组（共 3 条，逐条证据一条不少）` | 前半是好的总结；括注里"共 3 条"是重复计数，"逐条证据一条不少"是纯解释 | 只留「同类发现已归并为 3 组」|

可复用的说法：**介绍性文字不是功能字段**。一个字段只有在"删掉它用户就做不成这件事"时才留；
而"讲我们怎么想的""把屏幕念一遍""保证我们知道得很多"都不属于这一类。
### 12.3.2 第三次反馈补充的两类（2026-09-19，用户逐条举例）

| 类 | 实例 | 为什么删 |
|---|---|---|
| **复述控件的当前值** | 选择器上方那行 `诊断目标：pm-ui-task48-other` | 选择器本身就把值显示在那里；再用一行文字写一遍是同一事实出现两次 |
| **控件内部再写一遍旁边标记已经说了的事** | 选择器选项标签里的 ` · 当前环境` 后缀 | 选择器**旁边**已有「非当前环境」标记；列表项里再拼一个后缀是把同一事实说两遍。**载体只留一个**：留控件旁的标记，删控件里的后缀 |
| **指路式引导** | `修改请到「环境」子页。` | 目标页就在同一排标签里可见，用户发现改不了时会自己点过去。**这是引导式交互，不是需要写出来的说明** |

**这条修订了我先前的一个判断**：我曾把 `修改请到「环境」子页。` 归为"可执行出路"而保留。
正确的切分是——**"出路"指的是给出具体命令、参数、文件名这类用户照做就能完成的信息**（例如 `dshpmc analyze --profile X`、
要改的文件与行号）；**而"去另一个页面"不算出路**，因为导航本来就摆在界面上。

**配套的界面要求**：删掉"指路"的前提是**目标入口在屏幕上可见且可点**。
所以在删「修改请到「环境」子页。」的同时，断言必须证明那个标签真的在（§12.5 的替代载体）。

同类检查的口径：凡是**同一屏里同一事实出现两次**的地方都要处理——包括"控件值 + 文字复述"与"状态句 + 标记"。
### 12.3.3 不允许用"没有标记"来表达状态（2026-09-19，用户第三次反馈的后续）

删掉选择框里的 ` · 当前环境` 后缀之后暴露了一个更深的问题：**"这个目标是不是当前环境"只剩"没有标记"一种表达**——
选中当前环境时界面上一片安静，用户只能从"没有那个标记"去推断。

这和我们一直在防的那一类是同一个家族：**把"没查"画成"没问题"**、以及 §12.5 的"删信息必须证明替代载体还在"。
共同的判据是——

> **一个事实要么在屏幕上被明确说出来，要么它就该被删掉；不能靠"缺席"来传达。**

所以：**「非当前环境」有标记，「当前环境」也要有标记**（用一个中性色标记，不是警告色——它不是问题）。
两边都有，才是"表现对齐"的实质含义：用户不需要比较"有还是没有"，直接读到状态。

反例边界（什么时候"缺席即状态"是可接受的）：**当缺席本身就是用户要看的那个量**的时候。
例如列表里"没有发现问题"就是结论本身；但如果某个标记的**存在**意味着"要注意"，那它的缺席就会被读成"没问题"，
而"没问题"是需要被证明的，不能靠没写。

### 12.4 护栏

标准要靠检查才立得住：`tests/ui-copy.test.mjs` 扫描 `src/client/locales.ts`，
对禁止词表做断言（同时覆盖 zh 与 en），并断言 intro 类文案不超过一句话的长度上限。

2026-09-19 补充：上面三类实例说明**词表 + 句长上限不够**——那三条当时全都能过检查。护栏要加三条：

1. **intro 不得枚举「界面上已渲染的元素名」**：`.intro` 里出现 3 个及以上**已渲染元素的名字**即判失败
   （直接抓住「依赖、组合、运行时、一致性、生态」这种把屏幕念一遍的写法）。

   ⚠ 这条最初被写成"出现 3 个及以上以 `、` 分隔的枚举项即失败"——**那是过钝的形态规则，会误杀合法枚举**。
   理由才是判据：**"把屏幕上已经显示的东西又念一遍"**。所以护栏要拿一份显式的「已渲染元素名」清单去比，
   清单每一项注明它渲染在哪里；光看顿号数量不算数。
   边界样本：`社区索引里的插件、技能与预设。` 若市场页上确实渲染了这三类（分类/标签），它就是重复，删；
   若没有渲染，它是在告诉用户"这份索引覆盖三类东西"，属合法信息——两种情况必须给出屏幕证据，不能靠句式推定。
2. **禁止"意图说明"句式**：`默认…`、`…即可`、`…一条不少`、`…不言自明` 这类以解释为目的的收尾，进禁止词表。
3. **状态句改标记**：`本页只读` 这类状态描述进禁止词表；状态要用界面标记（Tag/Badge）表达。

每条禁止项都要**注明它来自哪次真实反馈**（删掉的原文 + 日期），这样后面的人知道为什么它被禁，
而不是把它当成一条凭空的洁癖。
**范围**：这套标准管 **UI**。CLI（`dshpmc`）是纯文本界面，**没有标记可用**——它的「状态句」是唯一表达形态，
不适用「状态要改成标记」那一条；`--help` 里的 `(read-only)` / `(exit 1)` 这类括注是**帮助信息**，保留；
命令输出里的「你接下来可以这样装」是**可执行出路**，保留。
反过来，**纯粹的背景介绍与教学句在 CLI 里同样要删**——判断标准与 UI 一致：删掉它用户还能不能完成任务。
### 12.5 删信息的人，负责证明它已在别处可被看见（2026-09-19）

删一句"重复屏幕已有信息"的文案时，**删除的合法性依赖那个前提**：屏幕上真的已经有它了。
所以删的人必须同时做到两件事，否则这次删除是**把一个事实从界面上拿掉**，而不是去掉冗余：

1. 说清**屏幕上哪里已经有了**（哪个元素、哪一行、哪个 Tag）；
2. **让测试钉住那个替代载体**——不能只把断言的字面跟着文案一起放松。

实例（本轮真实发生）：`health.grouped` 的括注被删，理由是"计数由组头 `health.groupCount` 承担"；
那么断言除了检查新的总结句，**还必须检查组头那串计数真的渲染了**。
`health.foreignTitle` 的「（不是当前环境）」被删，理由是"由「非当前环境」Tag 表达"；
那么断言就必须检查那个 Tag 真的在。

反模式：把断言从「…（共 173 条」改成「…」，然后什么都没补——测试绿了，保证没了。
